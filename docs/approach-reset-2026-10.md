# アプローチ再設定（2026-10）: 「コードが決め、LLMが言葉にする」から「コードが事実と論理を保証し、LLMが考えて話す」へ

## この文書の位置づけ

目標は変わっていない。**人間1人 + AI16人の17人村で、かつて人間同士で遊んだチャット人狼と
同じ体験ができること**である。AIの発言と思考が、少なくとも人間のプレイヤーに「見える」
水準に達する必要がある。

変えるのは、そこへ至る経路である。この文書は、現在の経路のどこが律速になっているかを
実測で示し、経路を切り替える判断と、切り替え後の完成条件を定める。

`docs/architecture.md`（v2の設計）、`docs/self-play-training.md`（自己対戦RL）、
`docs/real_game_log_reasoning_plan.md`（実ログ基盤）はいずれも有効な記録として残すが、
**優先順位についてはこの文書が優先する**。

---

## 1. 結論（先に書く）

1. 律速段階は「推理の精度」でも「学習の計算量」でもなく、**設計の置き場所**である。
   v2はLLMから「考えること」を取り上げ、言い回しだけを残した。結果、卓は正しいが
   人間に見えない。同時に、人間らしさを本来担うはずのLLM呼び出し自体が、推論モデル
   向けに調整されておらず半数が失敗している。
2. **自己対戦RL（Transformer/PSRO）と実ログ学習パイプラインは、完成への最短経路から
   外す**。コードは残すが、これ以上の投資をしない。
3. 新しい経路 **v3** を入れる: コードは事実台帳・論理ソルバー・検証・発言順・公開義務
   （結果を出す、COする）だけを担保し、**誰を疑うか・投票・夜行動・発言内容はLLMが
   「盤面メモ」を読んで決める**。発言はチャット調で、定型文は挿入しない。
4. 完成条件を「人間らしさ」の実測指標で定義し、v3 をその指標で評価してから既定にする。

### 2.2 同じ対戦で起きていた推理の破綻

- **共有者2人CO = 「対抗」扱い**。`BeliefEngine._contests` は「同じ役職のCOが2人以上」を
  対抗と判定していた。共有者は定員2なので2人COは正常な形だが、村人4席が4日間
  「共有COが2人いて少なくとも1人は偽」と繰り返し、**2日目に真の共有者(p3)が処刑された**。
  人間は絶対にしない誤りである。本PRで修正した（`ROLE_DEFINITIONS[role].count` を超えた
  場合だけ対抗）。
- **狼チャットと襲撃の分断**。狼は1日目・2日目の夜に「p8（真占い）即噛み」と相談したが、
  襲撃先はコードが信念エンジンから別に決めるため、p8は最終日まで生存した。
  v2では「2つの推論系が並走する」ことを発言と投票については潰したが、夜については残っていた。
- **騙り計画の不発**。偽霊媒を割り当てられた狂人(p7)は5日間で一度も公開発言せず、
  騙りCOもしなかった。必須発言者の仕組みは「結果を持つ席」「CO予定の席」を拾うが、
  席が選ばれても生成が途中切れすれば何も起きない。

### 2.3 3本の線路がそれぞれ止まっている理由

**(a) v2「コードが決め、LLMが言葉にする」**

- 発言の中身（結論・根拠・確度・第二候補・反対材料）は固定文言のブリーフとして渡され、
  モデルは「上の結論・根拠・数値は変更しないでください」と指示される。16席が同じ
  ブリーフ構造を復唱するため、`docs/architecture.md` が警戒した「17個の帽子をかぶった
  1人」が、今度はブリーフ自身によって再現されている。
- 推理の深さは信念エンジンの証拠カテゴリ8種（公開黒・白・対抗・確定済み席への投票・
  多数派圧・告発・誤引用）で頭打ちになる。人間の17A推理（内訳、囲い、身内切り、
  占い先指定、狐ケア、縄計算からの吊り順）はここにない。足すには1カテゴリごとに
  コードと重みを書く必要があり、それが進まないことが律速になっている。
- v2 の最大の成果（事実台帳・z3ソルバー・検証・監査・公開情報境界）は、
  「モデルに決めさせない」こととは独立に価値がある。これは残す。

**(b) 自己対戦RL（`backend/app/training/`、約11,500行、直近50PRのうち38本）**

- 学習対象は構造化された意味行動（CO/判定/投票/夜行動の離散選択）であり、
  自然言語は入っていない。「人間の発言→意味解析」「学習済み行動→LLMで文章化」は
  いずれも未着手（`docs/self-play-training.md` の Next stages 5, 9）。
- 報酬は終端の勝敗のみ（+1/-1/0）、17人の隠匿情報ゲームで、パイロットは数千試合。
  同文書自身が「10万試合以上で初めて評価に値する」と書いている。1人の開発者が
  GPUを借りて回す規模ではない。
- 仮に強い方策が得られても、**自己対戦で収束した慣習が人間の慣習と一致する保証はない**
  （公開で「人狼」とCOする、初日に全員黙る、など）。目標は「強い」ではなく
  「かつての人間のように見える」である。
- したがってこの線路は、目標に対して**遠回りかつ到達保証がない**。研究資産としては
  残し、完成の critical path から外す。

**(c) 実ログ学習パイプライン（るる鯖17Aの training-ready ゲート）**

- 2試合をケーススタディ、8カットオフを専門家注釈。しかし元HTMLの取得・公開版/完全版の
  整列・正規イベント化は未完で、`CLAUDE.md` の規約どおり1試合も training-ready に達して
  いない。ゲートの設計は正しいが、**重み学習の前提としては完成が遠い**。
- 一方で、ケーススタディに書かれた教訓（「最も狼らしい人」と「今日吊るべき人」は別、
  噛まれた占い候補が真とは限らない、死んだ真候補視点のグレーは「安全」ではない、
  能力対象は負け筋に従う）は、**そのまま日本語でLLMに渡せる知識**である。
  学習データではなく、プロンプトのドクトリンとして即座に使える。

### 2.4 律速段階の正体

「人間らしい発言と思考」を得るための手段として、**(a)はLLMから思考を取り上げ、
(b)はLLMを使わず、(c)はLLMを使う前にデータ基盤の完成を待っている**。
三つとも、2026年のLLMが最も得意な「構造化された事実をもとに、人格を持って日本語で
推理し、話す」ことを、設計上使っていない。これが律速である。

## 3. 方針転換の原則

> **コードは「何が事実か」「何が論理的に不可能か」「何を言う義務があるか」を保証する。
> LLMは「何が怪しいか」「何を言うか」「誰に入れるか」「夜に何をするか」を決める。**

- 事実（CO・判定・投票・死亡・時系列）はコードが台帳から正確に出す。LLMに記憶させない。
- 論理（配役の定員、公開情報から確定すること、時系列の矛盾）はソルバーが出す。
  LLMに数えさせない。
- 不可能な出力（死者を吊る、公開した白を黒に反転、CO無しの結果公開）は検証で修正する。
  **「誰が人狼かを読み違える」は人間らしい誤りなので修正しない**（v2の方針を踏襲）。
- ソフトな推理と戦略（内訳、吊り順、囲い読み、CO時機、襲撃先）はLLMが人格と役職で決める。
- 発言と投票の一貫性は「上書き」ではなく、「自分が昼に推した相手」をモデルに見せ、
  変えるなら理由を言わせることで保つ。ずれは監査に残る（v2と同じ）。

## 4. v3 の構成（本PRで実装）

`WEREWOLF_REASONING_ENGINE=v3`。**既定は v3**（2026-10-03 に切り替えた。当初は §6 の評価を
通してから切り替える方針だった。§6.1）。

| 層 | 担当 | 実装 |
|---|---|---|
| 事実 | コード | `PublicFactLedger`（既存） |
| 論理 | コード | z3 `RoleSolver`（既存）、`timeline.py`（既存） |
| 盤面の提示 | コード | **新規** `reasoning/board_memo.py`: 生存/死亡、CO一覧（共有の相互確認を含む）、判定一覧、投票表、公開情報だけで確定すること、時系列の矛盾、席だけが知ること。**名前のみ、IDなし** |
| 発言順・必須発言者 | コード | `select_opening_speakers` / `required_claim_speakers`（既存） |
| 公開義務（結果・CO） | コード | `DiscussionDecision.required_public_results`（既存）を「この発言で必ず言うこと」として渡す |
| 疑い・吊り先・投票・夜行動 | **LLM** | `DiscussionOutput.reasoning_memo.execution_target` を採用。`enforce_execution_target` は適用しない。投票・夜行動はモデル呼び出し |
| 発言 | **LLM** | チャット調のシステムプロンプト（`context.py` `_layer_a_chat`）、縮小した出力契約（`CHAT_DISCUSSION_OUTPUT_INSTRUCTION`）、人格ごとのチャット例文、17A用語ドクトリン（`knowledge/jinro-17a-chat-register.md`、v3限定） |
| 検証 | コード | `validate_discussion_output`（既存）。不正な対象は決定論的に修正 |
| 監査 | コード | 決定監査・投票変更分類（既存）。v3では `decision_target` = モデルの検証済み対象 |
| 狼チャット | **LLM** | 各狼が発言し、襲撃プロンプトに狼チャットの履歴が入る（分断の解消） |

LLMプロバイダには `LUNA_REASONING_EFFORT`（`low`/`medium`/`high`、空=送らない）を追加した。
エンドポイントが拒否した場合は1回の400で学習して以後送らない。推論トークンが
completion の7割を占める現状への、最初に回すべきつまみである。

## 6. 完成の定義と計測

「人間に見える」を測れる形にする。`scripts/evaluate.py` のレポートに次を追加した
（`app/eval/analyzers.py`）。

| 指標 | v2 ライブ実測 (gpt-5.6-luna, seed 11) | v3 の目標 |
|---|---|---|
| 定型句を含むAI発言率 | 98% | **0%** |
| 「(pN)」表記を含むAI発言率 | 100% | **0%** |
| 1日あたり公開発言数 | 約10 | **40以上**（最終的には人間の卓に近い80〜150） |
| 公開発言の平均文字数 | 150字超 | **30〜80字**（CO・整理のみ長い） |
| LLM呼び出し成功率 | 49% | **95%以上** |
| 公開発言1件あたりの待ち | 28秒 | **5秒以下**（§7 Phase C） |
| 人間判定 | 未計測 | 1日分のログを提示し、評価者が「AI/人間」を当てる正答率が **60%以下** |

加えて、推理の正しさについては既存のものを使う:

- 状態破損ゼロ（死者を対象にしない、白黒反転なし、投票履歴の誤認なし）: v2 と同じく 0 を維持
- 専門家カットオフ評価（v2版）の `plan utility` と `catastrophic avoidance`: v2 ブリーフを上回る
- 共有者の相互確認済みペアが「対抗」として語られない（回帰テスト追加済み）

### 6.1 初回ライブ結果（gpt-6-luna、シード1。§2.1b）

| 指標 | v2 | v3 | 目標 | 判定 |
|---|---|---|---|---|
| 定型句を含むAI発言率 | 100% | 6.4% | 0% | ほぼ達成（残りはモデルが拾ったプロンプト語彙） |
| 「(pN)」表記を含むAI発言率 | 100% | 0% | 0% | 達成 |
| 1日あたり公開発言数 | 12.9 | 9.8 | 40以上 | 未達（Phase C） |
| 公開発言の平均文字数 | 172 | 86.9 | 30〜80字 | ほぼ（上限をやや超える） |
| LLM呼び出し成功率 | 76.5% | 100% | 95%以上 | 達成 |
| 議論1回の待ち | 51.4秒 | 18.0秒 | 5秒以下 | 未達（Phase C・思考量） |
| 人間判定 | 未計測 | 未計測 | 60%以下 | これから |

**v3 を既定にする条件**: ライブ対戦2試合で上の指標を満たし、人間（開発者）が
トランスクリプトを読んで「かつての卓に近い」と判断すること。

**2026-10-03 の判断**: v2 に対する v3 の優位は、同一モデル・同一シードで明確（§2.1b）。
未達の項目（発言数・待ち）は v2 のほうが悪いか同じで、v3 を既定にしない理由にならない。
開発者の判断で **v3 を既定にした**。

### 6.2 開発者の読み（2026-10-03）

run #11 の対戦記録を読んだ開発者の評価:

> 推論はある程度の妥当性を持つようになってきている。方向性は正しい。しかし、まだ
> かつての体験には遠い。相手の意見に耳を傾けて自分の意見を変えるなども欲しい。
> もちろん筋が通っている場合は、だが。

つまり §6 の数値目標の手前に、**「聞き入れて意見を変える」という行動が足りない**。
run #11 の記録で、同じ人の連続する発言のあいだで疑い先が変わった回数を数えると、78発言
中17回あった。しかしそのうち11回は、疑い先本人が処刑・襲撃で死んだための変更で、
自発的な変更は6回（うち同じ日のうちは4回）しかない。さらに、新しい事実や相手の言い分を
受けて変えたと読めるのは2回（ケントの新しい占い結果、ツムギが「根拠が薄いと認めた点は
受けて疑いを下げる」と言った場面）だけで、残りの4回は人狼カイトが同じ日のうちに狙いを
入れ替えたものだった。議論のなかで誰かの指摘を受けて考えが動く場面が、ほとんど無い。
原因の一つはプロンプトで、v3 には、相手の指摘に耳を傾けて考えを変えるよう求める記述が
無く、前回の発言のあとに何が起きたか（自分宛ての発言、自分の推し先への反論、新しい結果）
もまとめて渡していない。
これを Phase B の項目に加える（§7 Phase B の5）。

## 7. 実装順序

### Phase A（本PR）

- v3 エンジン、盤面メモ、チャット調プロンプト、縮小出力契約、名前のみ表記、
  各狼の夜チャット、投票/夜行動のモデル決定、`LUNA_REASONING_EFFORT`、
  人間らしさ指標、共有者対抗バグ修正、テスト。

### Phase B（ライブ確認とドクトリン）: 1〜2週間

1. `WEREWOLF_REASONING_ENGINE=v3 LUNA_REASONING_EFFORT=low` で `scripts/evaluate.py --games 2`。
   成功率・途中切れ率・定型句率・発言数を確認。途中切れが残るなら出力契約をさらに削る
   （`public_results` と `directed_questions` 以外は任意にできる）。
   **（済: 思考量を指定しない1戦。途中切れは 0、成功率は 100%。結果は §2.1b・§6.1・§10。
   思考量 `low` の比較は §10.5 の2番。）**
2. 2本のケーススタディ（`docs/case_studies/`）の「再利用できる教訓」を
   `app/ai/knowledge/` のドクトリンに移す（v3限定・役職別）。
3. 人格ごとのチャット例文を実ログの口調に寄せる（権利上、原文は入れず特徴だけ）。
4. 専門家カットオフ評価を v3 のプロンプト（盤面メモ形式）で回し、v2 と比較。
5. **意見の更新（§6.2）**: 相手の指摘・反論・新しい事実に耳を傾け、筋が通っていれば
   自分の疑い先・投票先・主張を変える。通らなければ、理由を言って変えない。変えるとき
   は誰のどの指摘かを言う。コードは「何が新しい事実か」「指した発言が実在するか」を
   保証し、筋が通っているかはモデルが判断する（§3 の原則）。評価には意見の更新率と、
   理由のない揺れ・撤回を言ったのに変わらない行動を数える指標を足す。
   **（実装済み: §10.6。効果は再戦の記録で確かめる。）**

### Phase C（体験の速度）: 1〜2週間

- 発言キューの並列生成: 次に話す予定の2〜3席の生成を同時に走らせ、ペーシング付きで
  順に表示する（`LUNA_MAX_CONCURRENCY` は既にある）。
- 1発言の長さを人格で短く、1日の発言数を増やす（`max_total`・`talkativeness` の再調整）。
- 人間の発言への即時反応: 名指しされた席と、直前の発言者だけを即座に生成する。
- UI: タイピング表示の複数同時化、短文の連投に合わせた表示密度。

### Phase D（人間判定）: 継続

- 1日分のログを提示して「どの発言がAIか」を当てる簡易テストを `scripts/` に追加。
- 判定結果を Phase B のドクトリン・例文に戻す。

### やらないこと

- RL の再開、実ログパーサー、重み学習。
- v2 ブリーフの改良。
- 人間の発言の高度な意味解析（v3 は人間の文章を**そのままログとして**LLMに読ませる。
  v2 の狭い正規表現による事実訂正はそのまま動く）。

## 10. v3 初回ライブの発見（run #11、2026-10-03）

8日・98発言の対戦記録を通して読み、数値に出ない欠陥を3つ見つけた。いずれも
「コードが事実を保証する」側の欠陥で、モデルの出来とは別である。

### 10.1 引用した他人の結果が、本人の結果として公開記録に載った（修正済み）

- **現象**: 本物の占い師ケントが「ダイキ、アオイのソウタ白はカイトを占った結果ではない」
  と反論しただけで、「ケント→ソウタ=白」が公開記録に載った。同じ夜に二つの結果を
  出したことになり、盤面メモに「時系列の矛盾」が載り、ケント自身が「記録ミスです」と
  存在しない結果を撤回し、狼のカイトがその矛盾を4日間にわたって攻撃材料に使った。
  偽占いの狼ダイキも「ケントのカイト黒だけで…」と言っただけで「ダイキ→カイト=黒」
  （身内切り）が記録に載り、5〜8日目の議論は「両黒」「身内切り」という、実在しない
  事実の上で進んだ。
- **原因**: `app/ai/public_speech.py` の `detect_public_results`（発言文から結果を拾う処理）
  が「Xの対象白」の所有格を見ず、発言者本人の結果として登録していた。宣言
  （`public_results`）が空の手番では文面の読み取りが使われる設計なので、v2 でも人間の
  発言でも起こる。
- **修正**: 「Xの対象白」「X→対象=白」「Xの占い/霊結果で…」を第三者の結果として除く
  （直後に一人称があれば発言者本人の結果に戻す）。
- **評価の盲点**: 既存の検査は宣言された `public_results` だけを見ていたので、レポートには
  何も出なかった（出たのは §10.3 の誤検出2件だけ）。公開記録そのものを、実際の占い・
  霊視の記録と突き合わせる検査を足した（`true_role_result_without_record`、
  `undeclared_spoken_result`）。run #11 の記録に当てると、この2件の偽の結果だけを
  過不足なく検出する。

### 10.2 同じ質問への繰り返し返信（修正済み）

- **現象**: カイトは、5日目にマコトから聞かれた質問に、6・7・8日目と続けて同じ趣旨で
  答えた。ソウタ・ダイキ・ツムギは同じ日に連続して二重に返信した。
- **原因**: 名指しの質問は、答えた発言の `reply_to` がその質問の発言IDと一致したときだけ
  消える。モデルは1回の発言で1つのIDしか指せず、3人から同じ質問を受けると2つが残る。
  残った質問は次の手番のプロンプトに再び「最初にこれへ答えてください」と載り、その日の
  返信機会も再び与えられた。
- **修正**: 質問は、プロンプトに載せた手番のあとで「消化済み」にする（記録は残し、
  「聞かれたが返信IDで結ばれなかった」数は評価で数え続ける）。プロンプトにも、まとめて
  答える・`reply_to` を入れる・繰り返さない、と明記した。

### 10.3 評価の誤検出（修正済み）

「人狼が仲間を明示的に狼視」（high）の2件は、「黒**だけで**…」の「黒だ」を断定と読んだ
誤検出で、人狼が仲間を名指しした事実はなかった。助詞の「だけ」を除いた。

### 10.4 まだ残っていること

- 1日あたり発言数 9.8、議論1回の待ち 18 秒。v3 の目標（40件以上 / 5秒以下）に遠い。
  待ちの84%は議論の逐次生成（78回 × 18秒）。Phase C。
- 応答のタイムアウト既定（30秒）が、v3 の p95（26.7秒）に近い。v2 は同じ30秒で36回
  タイムアウトした。60秒への引き上げを検討する。
- 同じ語彙が会話内で連鎖する（「独立した根拠」）。プロンプトから該当語を外す。

### 10.5 次の一手

1. §10.1・§10.2 を直した版で v3 をシード1でもう1戦し、偽の結果・繰り返しが消えたことを
   記録で確かめる（進捗はログに流れる）。
2. 同条件で `reasoning_effort=low` の1戦。待ち・コスト・発言の質の差を見る
   （推論トークンが出力の78%）。
3. v3 を既定にする（§6.1）。**（済み）**
4. Phase C（並列生成、発言数）。

### 10.6 「聞き入れて意見を変える」の実装と測り方（§6.2）

モデルに相手の言葉を聞かせる仕組みを、プロンプトの側から入れた。コードは「何が前回の
発言のあとに出たか」という事実を保証し、筋が通っているかどうかはモデルが判断する。

1. **前回の発言のあとに出たこと**（プロンプトの層）: 自分が前回推していた吊り先、自分宛て
   の発言（返信されたか、名前を呼ばれた）、推していた相手に触れた発言、新しく公開された
   結果・CO。名前だけで書き、ID は入れない。名指しの質問は専用の層に出るので重ねない。
2. **聞き入れ方の指針**（システムの層）: 筋が通っている指摘や新しい事実は認めて、疑い先・
   吊り先も実際に変え、誰のどの指摘かを一言で言い、その発言に `reply_to` を向ける。通ら
   なければ変えずに理由を言う。強く言われただけで折れない、多数に合わせるだけで変えない。
   「認める・撤回する」と言ったらそのとおり動く。人狼・狂人・妖狐は陣営の目的を優先する。
3. **人格ごとの聞き方**（17種を `open` 6 / `normal` 6 / `firm` 5）: 「確かに」とすぐ認めて
   変える人、決定的な根拠が出たときだけ変える人。全員が最初の反論で折れる卓、全員が
   折れない卓にならないようにする。口調の例にも、認める言い方・譲らない言い方を1つずつ足した。
4. **返信先の記録**: 各発言が何に返信したかを記録に残す（`Utterance.reply_to`）。
5. **評価の指標**（レポートの §3）: 疑い先の自発的な変更（疑い先の死亡による変更は除く）、
   うち同じ日のうちの変更、相手の発言に返信しての変更、認める言葉を伴う変更、
   「認める・撤回する」と言いながら疑い先が変わらない発言。

**基準線（run #11、v3・指針なし）**: 64の後続手番のうち、疑い先の自発的な変更は6回
（9.4%、うち同じ日のうち4）、そのうち認める言葉を伴うのは4回、疑い先の死亡による変更は
11回、認める・撤回すると言いながら変わらない発言は9件。v2 は疑い先をコードが決めるので、
この指標の比較対象にならない。

**確かめること**: 次の再戦の記録で、自発的な変更が増えるか、「認めると言って変わらない」
が減るか、変えた発言が誰の指摘かを言っているか、を読む。数値の目標は、人間の卓での実測が
無いので、まだ置かない。折れすぎる（理由のない揺れ）場合は、`firm` の比率と指針を見直す。

## 11. 実LLMプロバイダを Anthropic に切り替える（2026-11-16）

### 11.1 決定

実際のLLMプロバイダを、luna（OpenAI互換API、gpt-6-luna）から **Anthropic の Claude API** に
切り替える（`WEREWOLF_LLM_PROVIDER=anthropic`）。既定モデルは `claude-opus-5-5`
（Claude Opus 5.5）。実装は `app/ai/provider/anthropic_claude.py`。

| 理由 | 中身 |
|---|---|
| APIクレジット | オーナーは Anthropic の API クレジットを潤沢に持っている。費用が律速でなくなり、全席を同じ上位モデルにでき、試合数を増やして「1試合で判断する」のをやめられる |
| 品質 | v3 はモデルが盤面メモを読んで考え、話す設計（§3）なので、モデルの推理と日本語の質がそのまま卓の質になる。Opus 級のモデルを全席に置く |
| luna の扱い | 削除しない。`WEREWOLF_LLM_PROVIDER=luna` で今までどおり選べる、休眠中の選択肢として残す。`LUNA_*` の設定も変えない |

これまでの計測（§2.1b・§6.1・§10.6）は gpt-6-luna の値である。Claude での試合は基準線を
一から取り直し、luna の値と前後比較しない（§11.6）。

（2026-11-16 追記: 最初の試合とレイテンシ測定のあと、ゲームのモデルを Claude Sonnet 5.5
（`claude-sonnet-5-5`）に変えた。Opus 5.5 は選択肢として残る。§11.8。）

### 11.2 変えること

**設定の名前は `WEREWOLF_ANTHROPIC_*`。** Anthropic の SDK は、引数が無ければ
`ANTHROPIC_API_KEY`・`ANTHROPIC_BASE_URL` などを環境から黙って読む。開発者の端末や
Codespaces には、別のツールのためにそれらが入っていることがある。そのまま読むと、別の
ツールのキーで課金したり、別の接続先へ要求を送ったりしうる。そこでアプリは自分の名前空間の
変数だけを読み、キーと接続先を必ず明示して SDK に渡す。`ANTHROPIC_*` は読まない。

| 設定 | 既定 | 用途 |
|---|---|---|
| `WEREWOLF_LLM_PROVIDER` | `mock` | `anthropic` で Claude。`claude` やモデル名（`claude-…`）を入れても `anthropic` と読む。モデル名なら、`WEREWOLF_ANTHROPIC_MODEL` が未設定のときはそのモデルを使い、別のモデル名が設定されていれば起動時に止める（黙って既定の Opus 5.5 で課金しないため） |
| `WEREWOLF_ANTHROPIC_API_KEY` | 空 | キー。GitHub Actions の secret か Codespaces の secret にだけ置く |
| `WEREWOLF_ANTHROPIC_MODEL` | `claude-opus-5-5` | モデル |
| `WEREWOLF_ANTHROPIC_BASE_URL` | `https://api.anthropic.com` | 接続先 |
| `WEREWOLF_ANTHROPIC_EFFORT_DISCUSSION` / `_VOTE` / `_NIGHT` / `_CHAT` / `_DEFAULT` | `low` / `medium` / `medium` / `low` / `medium` | 呼び出し種別ごとの思考量（`low`・`medium`・`high`・`xhigh`・`max`。空は既定） |
| `WEREWOLF_ANTHROPIC_MAX_TOKENS` | 12000 | 1要求の出力上限の下限（呼び出し側の値と大きいほうを送る） |
| `WEREWOLF_ANTHROPIC_MAX_CONCURRENCY` | 8 | プロセス全体の同時要求数 |
| `WEREWOLF_ANTHROPIC_TIMEOUT_SECONDS` | 120 | 1要求のタイムアウト |
| `WEREWOLF_ANTHROPIC_MAX_RETRIES` | 2 | 再試行の回数 |
| `WEREWOLF_ANTHROPIC_FALLBACKS` | `default` | 拒否時のサーバー側フォールバック（`default` / `off`） |
| `WEREWOLF_SESSION_MAX_COST_USD` | 30 | 人間が遊ぶ1セッションあたりの推定費用の上限 |
| `WEREWOLF_ALLOW_OPEN_ACCESS` | `false` | `true` のときだけ、パスワード無しで課金のあるプロバイダ（`anthropic`・`luna`）のサーバーを起動できる（ローカル専用） |

**思考量は呼び出し種別ごとに決める。** Opus 5.5 は思考を切れない（`thinking` は送らず、
深さを `output_config.effort` で決める。モデルの既定は `medium`）。思考のトークンは
`max_tokens` に含まれ、出力として課金される。

- 議論と狼・共有チャットは `low`。発言は1件ずつ順に生成するので、1回の待ちがそのまま
  会話の速さになる（luna では議論1回の平均応答が 18.0 秒、出力の78%が推論トークンだった。
  §2.1b）。
- 投票と夜行動は `medium`。勝敗を直接決める。投票は席どうしで並列に走るので、思考を深くしても
  1日の待ちへの影響は議論より小さい。
- 振り分けはスキーマの名前で決める: `ChatDiscussionOutput`・`DiscussionOutput`・
  `BriefDiscussionOutput` は議論、`VoteOutput` は投票、`NightActionOutput` は夜、
  `WolfChatOutput` はチャット、それ以外（要約・判定・専門家評価など）は既定。
- **この既定は仮置き**で、Phase 1b のレイテンシ測定（§11.5）で確かめて決め直す。
- 出力上限は 12000 を下限にする。思考が上限を食うと JSON が閉じない。打ち切り
  （`stop_reason=max_tokens`）は `finish_reason=length` として記録するので、既存の
  「途中切れ」の集計がそのまま使える。

**`temperature` は送らない。** このAPIはサンプリングの引数を受け付けない（SDK には引数自体が
無く、API は400を返す）。プロトコルとしては受け取り、プロバイダで捨てる。gpt-6-luna でも
既に送っていなかったので（run #11 の接続確認「temperature=送信しない」）、失うものは無い。

**構造化出力と、v3 の発言スキーマ。** すべての要求に `output_config.format`（JSON schema）を
付ける。スキーマは `anthropic.transform_schema` で変換し、応答は Pydantic で検証し直す
（変換で最小値などの制約が説明文に移るため）。Anthropic の構造化出力は、1要求あたり
**任意パラメータ24個・union 型のパラメータ16個**を上限とし、超えると
400 "Schema is too complex for compilation" を返す。再試行では直らない。

- `DiscussionOutput` は入れ子まで数えると任意パラメータが36個ある。送ると文法の変換に
  400で拒まれる。プロバイダはそのスキーマを記憶し（下の「文法の変換に拒まれたスキーマ」）、
  同じ呼び出しを送り直してから、そのプロバイダ（評価では1試合、人間の卓では1セッション）が
  続くあいだ、議論の手番をすべてスキーマをシステムプロンプトに入れた寛容パース
  （`json_object` 経路）で送る。項目は残るが、文法による強制は無い。読めなかった手番は
  `AIPlayerAgent` の降格で `BriefDiscussionOutput`（`public_message` だけ）に落ち、
  CO・結果の公開・名指しの質問・吊り先がその手番から**黙って消える**。
- そこで v3 は **`ChatDiscussionOutput`** を送る。v3 のプロンプトが実際に求める8項目と、
  メモの代わりの `plan_note`（7項目）だけで、変換後は任意18・union 6。受け取ったら
  `DiscussionOutput` に戻すので、呼び出し側は今までどおり `DiscussionOutput` を受け取る。
- v2 と legacy は今も `DiscussionOutput` を送る（保守のみで、v3 の契約に移していない）。
  Claude では上の経路で議論が文法の強制なしに読まれるので、v2・legacy と v3 を Claude で
  比べると、議論の手番はパースの条件が違う。レポートの「うち strict schema で成功」が下がり、
  `summary.json` の `metrics.parse_path_counts` に `json_object` として出る。
- `backend/tests/ai/test_schema_complexity.py` が、v3 の試合と評価（判定・専門家ベンチ）で
  送りうるすべてのスキーマを上限の内側に留める。項目を足して上限を超えれば、ライブより
  先にここで落ちる。`DiscussionOutput` は上限を超えていること自体を確かめている。
- 文法の変換に拒まれたスキーマは、**そのスキーマだけ**を記憶し、スキーマをシステム
  プロンプトに入れた寛容パースに切り替える。luna の「strict 非対応を学習する」仕組みを
  プロセス全体に効かせると、1回の400で投票・夜行動までスキーマの強制が外れるため。

**「思考」を書かせない（`plan_note`）。** v3 のメモの項目は `overall_thought`・
`private_team_thought` で、プロンプトには「思考はreasoning_memoに書く」「前回の非公開思考メモ」
とあった。モデルに自分の思考を書き出させる要求は `reasoning_extraction` として拒否されうる。
しかもこの種類の拒否は、サーバー側のフォールバックでは再試行されない。その手番は単に失われる。
送る項目名を `plan`・`team_plan` にし、v3 に届くプロンプトから「思考」「thought」「reasoning」
という言い方を外した。v2・legacy のプロンプトは計測済みの文言のままにした。

**拒否時のサーバー側フォールバックは既定で有効。** 要求したモデルが拒否した手番を、同じ
呼び出しの中で別のモデル（`claude-opus-5`・`claude-opus-4-8`、$5/$25）が答え直す
（beta `server-side-fallback-2026-07-01`、`fallbacks="default"`）。人間の卓では、手番が
消えるよりよい。ただし基準線の試合に別モデルの手番が混ざるので、実際に応答したモデルを
呼び出しごとに記録し（`served_model`）、集計に `served_model_counts`・`fallback_served_calls`
を出す。API がこの beta を受け付けない場合は、全呼び出しを失敗させずにフォールバックを切る。

**費用: 単価表、予約と精算、上限を握りつぶさない。** 単価（100万トークンあたり USD）:

| モデル | 入力 | キャッシュ書き込み（5分） | キャッシュ書き込み（1時間） | キャッシュ読み | 出力 |
|---|---|---|---|---|---|
| `claude-opus-5-5`（既定） | 4 | 5 | 8 | 0.20 | 20 |
| `claude-sonnet-5-5` | 2 | 2.50 | 4 | 0.10 | 10 |
| `claude-haiku-5-5`（プロンプト10万トークン以下） | 0.10 | 0.125 | 0.20 | 0.01 | 0.50 |
| `claude-opus-5`・`claude-opus-4-8`（フォールバック先） | 5 | 6.25 | 10 | 0.50 | 25 |
| `claude-fable-5-2` | 8 | 10 | 16 | 0.20 | 40 |
| Opus 5.5 の fast mode | 8 | 10 | 16 | 0.40 | 40 |

上の3行は Anthropic の料金ページ（2026-11-15 取得）、下の3行は claude-api スキルの参照資料
（再取得していない）から。

- 単価表は `app/ai/provider/pricing.py`。usage（未キャッシュ入力・キャッシュ書き込み・
  キャッシュ読み・出力）から呼び出しごとの費用を出す。表に無いモデルは最も高い行で見積もる。
- `EvaluationBudget` は、HTTP要求を送る前に最悪の費用を予約し（`reserve`）、終わったら
  実際の費用で精算する（`settle`）。同時に走る要求が、1件分しか残っていない上限の下を
  そろってすり抜けることがない。
- 上限超過（`BudgetExceeded`）は握りつぶさない。プロバイダもエージェントもそのまま上へ
  投げる。これまでは定型の手番に化けて試合が続き、上限が試合中は効いていなかった。
- `scripts/evaluate.py --provider anthropic` は `--max-cost`（USD）を必須にする。人間が遊ぶ
  経路は、セッションごとに `WEREWOLF_SESSION_MAX_COST_USD`（既定30）で止める。
- **1戦の費用の見積もり（推定）**: run #11 のトークン量（入力 97.8万・出力 18.0万）を Opus 5.5 の
  単価に当てはめると、キャッシュ無しで約 $7.5（入力 $3.9 + 出力 $3.6）。luna のトークナイザと、
  思考量を指定しない gpt-6-luna の推論比率（78%）を流用した値で、±2倍程度の幅がある。
  正しい値は最初の試合の usage で取る。

**同時実行と再試行。**

- レート上限は API キーに付くので、同時実行の上限は試合ごとではなく、プロセス内のすべての
  プロバイダで共有する1つにする（`WEREWOLF_ANTHROPIC_MAX_CONCURRENCY`、既定8）。Start ティアでも
  Opus 5.5 は 4,000 RPM・入力 200万 TPM・出力 40万 TPM（キャッシュ読みは入力の上限に数えない）
  なので、1〜数試合の同時進行では制約にならない。それでも 429 と 529 で試合が壊れないようにする。
- SDK の自動再試行は切り、プロバイダが1本の再試行で扱う。接続エラー・タイムアウト・429
  （`retry-after` を守る）・5xx・529 は再試行し、拒否・途中切れ・その他の4xxは再試行しない。
- タイムアウトは120秒にした。luna の30秒は、v3 の p95（26.7秒）に近かった（§10.4）。

**開けたままでは起動しない。** キーを入れた時点から、サーバーに届く人は誰でも課金の試合を
作れる。公開デプロイの段階を待たずに、課金のあるプロバイダ（`anthropic`・`luna`）で
`WEREWOLF_ACCESS_PASSWORD` が空ならサーバーは起動を拒む（luna は料金表が無いので、セッションの
上限は金額ではなく要求数で掛かる）。`WEREWOLF_ALLOW_OPEN_ACCESS=true` のときだけ外せる（ローカルで自分だけが
使う場合に限る）。

**観測。** 呼び出しの記録（`CallRecord`）に、キャッシュの書き込み・読みのトークン、元の
`stop_reason`、拒否の種類（`stop_details.category`）、応答したモデル、request id、推定費用、
effort を足した。コードがモデルの代わりに埋めた箇所は、名前を付けて数える
（`brief_fallback`・`vote_code_resolved`・`night_code_resolved`・`wolf_chat_fallback_line`・
`obligation_posted_by_code`・`speech_discarded_after_phase_end`・`discussion_stalled`、
§11.8 で足した `designation_question_unanswered`）。
「動いた」ように見えて実はコードが代行していた試合を、集計で見分けるためである。

**接続確認。** `scripts/check_llm.py` に anthropic 用の事前確認を足した。試合を回す前に、
キー・モデル・ゲームが送る構造化出力のスキーマが通ることを、少ない呼び出しで確かめる。

**後回しにすること: キャッシュのためのプロンプトの並べ替え。** いまのプロンプトは席ごとの
内容が先に来るので、席をまたいでキャッシュできる部分が小さい。共通のルール・ドクトリン・
その日の内容を先に置けば、入力費は大きく下がる。それでも今は入れない。

1. 下がるのは主に入力費である。クレジットが潤沢ないま、費用は律速ではない。
2. 待ち時間への効果は小さい。議論の待ちを決めているのは生成と思考で（luna では1呼び出しの
   出力が平均約900トークン、その78%が推論）、キャッシュ読みが縮めるのは最初のトークンまでの
   時間だけである。
3. モデルが読むものが変わる（人格と役職カードが、その日の共通の内容のうしろに回る）。
   これは品質の変更なので、対にしたシードでの A/B と、基準線の取り直しが要る。

当面はキャッシュの書き込み・読みのトークンを記録するだけにする。Phase 3 で、最初のトークン
までの時間が呼び出し時間のうち無視できない割合だと分かったら、A/B を通して入れる。

  `WEREWOLF_LLM_PROVIDER=mock` と空の `WEREWOLF_ANTHROPIC_API_KEY` を明示する（念のための
  二重化）。キーは、手動実行だけの評価ワークフロー（`evaluate.yml`・

  `@pytest.mark.live_llm`（既定で除外）にする。
- §3 の原則（コードは事実・論理・義務、モデルは疑い・発言・投票・夜行動）。

### 11.4 同時に直す不具合（2026-11-15 の調査）

切り替えの前にコードを通読し、プロバイダとは独立の不具合を見つけた。どれもモックで再現・
検証できる。最初の有料の試合で既知の不具合を測らないよう、同じ変更で直す。

| 不具合 | 何が起きていたか |
|---|---|
| 全席に配る日次まとめが、非公開の吊り先を配り、共有者ペアを「対抗」と書く | まとめの論点に、各席の信念エンジン（その席だけが知る情報を含む）が出した処刑候補が「処刑候補が割れている」として載り、全席に配られていた。相互確認済みの共有者ペアを「対抗」と書いていた（§2.2 で真の共有者が吊られたのと同じ誤り） |
| 前日の「昼に推した吊り先」が残る | 投票プロンプトに出す「昼に推した吊り先」が日をまたいで消えず、前日の、すでに死んだ相手が出ることがあった |
| 必須発言者の重複で進行が固まる | 同じ席が必須発言者に二重に入ると、段階が `immediate` のまま進まず、その日の議論全体が1回の `POST /start-discussion` の中で走っていた |
| 生成に失敗すると公開義務が消える | 必須発言者（結果を持つ席・CO予定の席）の生成が失敗・拒否されると、結果もCOも出なかった。簡易契約への降格も `public_message` しか残さない。コードが台帳の事実の文を出す（`obligation_posted_by_code`） |
| 議論が終わってから発言が届く | 議論のフェーズが終わったあとに、生成中だった発言が投票フェーズへ投稿されていた（`speech_discarded_after_phase_end`） |
| 3回続けて失敗すると黙って止まる | 生成が3回続けて失敗すると、その日の議論が止まり、画面にも記録にも出なかった（`discussion_stalled`） |
| 夜のプロンプトに昼の議論が無い | v3 は夜行動と夜のチャットをモデルが決めるのに、そのプロンプトに当日の公開議論が入っていなかった |
| ドクトリンの「独立」 | v3 に届くドクトリンに「独立（した）根拠」が残り、モデルがそれを拾って言い合っていた（§2.1b・§10.4）。評価はこれを定型句として数える |

**Phase 1b: Claude の立ち上げと M1。**

2. レイテンシ測定: 記録済みの議論・投票のプロンプトを流し、ストリームで最初のトークンまでの
   時間・総時間・思考と出力のトークン・拒否を、Opus 5.5 の `low` と `medium`、fast mode、
   Sonnet 5.5、Haiku 5.5 で測る。議論のモデルと effort は、この結果で決めてから M1 に進む
   （決めたあとに替えると、基準線とドクトリンの調整をやり直すことになる）。
3. M1: Claude で1試合が完走し、次をすべて満たす。

| M1 の完了条件 | 値 |
|---|---|
| `release_gate` の HARD_FAILURE 項目 | すべて 0 |

**Phase 2: 基準線は計測であって、合格判定ではない。**

- 異なるシードを6〜8個、比べる条件のあいだで対にして使う。`evaluate.py` は2戦目以降のシードを
  1ずつ進め、指標を試合をまたいで合算するので、**1ジョブ1試合**で並列に回す（ジョブの
  上限は120分。effort を上げる、遅いモデルにするなど1試合が延びる条件では、まず1試合の
  所要を確かめてから回す）。
- 指標の単位で必要な試合数が違う。呼び出し単位（応答時間・費用・パース経路・拒否）は2試合でも
  読める。発言・手番単位（聞き入れ率、定型句率、文字数）は1条件あたり4〜8試合が要る
  （たとえば自発的な変更 9.4% と 19% を見分けるには、1条件あたり後続手番が約200、1試合64手番
  として約4試合）。勝率では判定しない。
- フォールバックで応答された呼び出しが多い試合には印を付け、比較から外せるようにする。
- 開発者が記録を通読する（§10 の欠陥は通読で見つかった）。

**Phase 3: 体験と推理の質を並行で。**

- 体験（§7 Phase C の残り）: 次に話しそうな数席を先に生成し、世代番号で古くなった出力を確定時に
  捨てる。人間に名指しされた席と直前の発言者は即座に返す。進行はブラウザの45秒タイマーを
  やめ、サーバーが主導する。1日の発言数を増やす。キャッシュの並べ替えと fast mode は、
  ここで測ってから決める。
- 推理の質（§7 Phase B の残り）: (1) 専門家ベンチの held-out の分割を先に決める。(2) v3
  （盤面メモ形式）の専門家ベンチを Claude で、1シナリオあたり10サンプル以上で回す
  （`temperature` が無いので、1回ではばらつきが分からない）。(3) ドクトリンは教訓単位で、
  出典を付けて移す（`docs/real_game_log_reasoning_plan.md` の AI 生成物の扱いに従う）。
  (4) held-out を分けて報告する。

**Phase 4: 人間判定の本格化と公開。**

- 1人 + AI16人のログをそのまま見せると約94%がAIの発言で、「全部AI」と答えるだけで当たる。
  AIと人間の発言を50/50にそろえ（名前は正規化する）、評価者を複数にし、約70〜270の判定を
  集める（正答率60%以下を片側95%で示すには、真の正答率が50%なら約70、55%なら約270が要る）。
- 公開デプロイ: WebSocket の認証、`/debug` の制限、ゲーム作成の上限、セッションの破棄。
  パスワードの必須化は Phase 1 に前倒しした（§11.2）。

### 11.8 最初の Claude 試合、レイテンシ測定、オーナーの判断（2026-11-16）

**最初の試合（Opus 5.5・v3・シード1・全席AI）。** 記録は
`backend/artifacts/live-v3-claude-opus55-seed1-2026-11-16/`（`report.md`・`summary.json`・
対戦記録、4つの観点で通読した所見 `analysis.md`）。1試合だけなので、数は挙動の手がかりで、
率の比較には使わない。

- 運用は M1 の条件をほぼ満たした。174呼び出しすべてが strict schema で成功し、再試行・拒否・
  フォールバックの応答・コードの代行はすべて0。$7.25・13分36秒。村の勝ち。
- ハード正しさは「理由のない投票先の変更」1件で不合格。通読では分類器の誤りだった（あとから
  出た他人の公開の論に説得された変更を数える区分がなく、比べる基準が卓に出ていない plan_note）。
  監査に載った票は69票中47票だけ。
- 主な問題（`analysis.md` §2 の P1〜P6）: ルール・配役の定員・確定事項がメモに無い（0日目の
  呪殺についてエンジンとソルバーが食い違い、死亡済みの妖狐を4〜6日目も生きている前提で話した）、

  - 勝敗の規則、縄の式の修正。
  - 占いCO者ごとの「真なら」の終局の行と、席ごとの終局の行。
  - 処刑ごとの霊媒結果（未公開）と「生存する霊媒COなし」。
  - 夜ごとの死体の有無と、死体なしの意味。
  - グレーの集合、0人も数えたCO数（3-0）。
  - 吊り先ごと・投票者ごとの投票（矢印の表記をやめた）。
  - 占い師の「人狼でも妖狐でもない」と「村側の騙りがなければ」の行、人狼の「事実と違う判定」と「真が色を偽らないなら」の行、狩人の「死体なしの夜」の行。
  - 自分の名前は「自分」。私的な結論の見出しに「匂わせない」。
  - エンジンは、人狼が1日目夜から毎晩、人狼以外を必ず襲撃することを強制する（コーディネーターは襲撃の無い夜にコードの襲撃を補い、それでも解けない夜を数える）。
- **プロンプト**
  - 前回メモに日付と出所、名前と現在の状態。
  - v3 の過去日の要約は1日1ブロック（夜の結果、まとめと本指定の原文、票、処刑者の最後の発言）。
  - 投票プロンプトに、票は公開されること、手番の回っていない席、進行役の方針の引用、候補の事実の印。
  - 投票と夜行動は決め手・理由を先に書く出力の順。
  - メモ欄の意味を「卓での立場」にし、人狼・狂人には本当の見立てを team_plan に。
  - 妖狐を秘匿の対象に入れ、陣営ごとの勝つ時点を役職カードに。
  - 用語の定義（3-0、グレー、グレランと指定、GJと平和、霊媒が生きていれば）。
  - 霊媒の促し。共有チャットの専用の指示と、前夜の内輪チャットを翌日に届ける。
  - 人格は口調と量だけ。
- **監査・記録**
  - COの再表明で最初のCOの日付を上書きしない。
  - 投票変更の分類（自分の結果を除く、関連する結果だけ、引いた論を優先）。
  - ゲートの新しい定義（上の evaluation.md の項）。run #13 と最初の試合を分類し直すと、ハードの不合格は seed 1・3 と最初の試合で0、seed 2 は1。
    - seed 2 の1件は、ホノカがその日の3行すべてでダイキの名を出しつつ最後の行で「ダイキさんは吊れません」と言ったもの。名前の有無では区別できず、意図を読む判定はしない方針のため残る。
  - 本文が相手を名指さない名指しの質問は捨て、相手に示す質問は本人の文から引く。陣営名の表示を1つの表に。

**有料の確認の前の統合レビュー（2026-11-17）。** 4つの領域を統合したあと、別のエージェントに通しで読ませた。情報の漏れ・人間の経路の破損・止まる進行はなかった。直したのは日の締めの読み方の3件と、細かい4件:

- **まとめが予算切れで飛ばされていた。** まとめは返答の予算が残っているときだけ出ていた。2日目以降の一言の手番が増えた分だけ予算が尽きやすくなり、模擬の試合で39日中6日が誰も名指さないまま投票に入った（修正前の版では41日中2日）。まとめは日を閉じる行なので予算の外で必ず出し、進行の総数に数える。まとめ役が誰もいない日は `summary_without_speaker` として数える。
- **「グレランで、仮指定はダイキ」をグレランの宣言と読んでいた。** run #13 の seed 3 で2回。指名された席が弁明せず、本指定もなかった。同じ行が「指定」と言う（「指定なし」「指定はしない」を除く）か、自分のメモの吊り先の名を出していれば、宣言ではなく指定として扱う。
- **共有チャットに「どちらがまとめ役か」を聞いていた。** 進行役はコードが決める（生存している、最初に共有COしたAIの席）。チャットで決めたことは無視され、決めた方と違う方が進行することがあった。問いを外し、コードが選ぶ席を名前で伝える。まだCOが無いときは「先に共有COした方」と伝え、人間が相方ならAIの席が務める。
- 細かいもの:
  - まとめと本指定のメモの吊り先は、モデルが書いた本文がその席を名指すときだけ候補にする。卓が聞いていない指名に弁明の手番を出さない。
  - コードが補う襲撃は、通常の「コードが決めた夜行動」とは別の `night_code_bite` として1晩1回数える。
  - v3 の「推し先」の残りを「メモの吊り先」に揃える。
  - 人狼の代表が死んだあとの代表の選び直しを、ゲームのシードから決まるようにする。同じシードの再実行で襲撃者が変わらない。
