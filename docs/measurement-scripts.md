# 計測スクリプト: レイテンシ測定と人間判定

`docs/approach-reset-2026-10.md` §11.5 の Phase 1b（レイテンシ測定）と Phase D・Phase 4
（人間判定）のための2本のスクリプトの説明。どちらも、ゲームの評価
（`scripts/evaluate.py`、`docs/evaluation.md`）の代わりにはならない。答える問いが別である。

| スクリプト | 答える問い | 費用 |
|---|---|---|
| `backend/scripts/latency_sweep.py` | どのモデル・effort・速度なら、1発言あたり約5秒（§6 の目標）で答えられるか | `--dry-run` はゼロ。実測は有料（`--max-cost` で上限） |
| `backend/scripts/human_judgment_quiz.py` | 評価者は、AI の発言と人間の発言を見分けられるか（正答率60%以下が目標） | ゼロ（ファイルを読むだけ） |

## 1. レイテンシ測定（`latency_sweep.py`）

### 1.1 何を答えるか

議論のモデルと effort は、Claude の基準線（Phase 2）を取る**前に**決める。決めたあとで
替えると、基準線とドクトリンの調整をやり直すことになる（§11.5）。この測定は、ゲームが
実際に送るプロンプトを候補の条件で流し、次を測る。

- 最初のストリームイベントまでの時間、最初の本文（text）が届くまでの時間、完了までの時間
- usage（未キャッシュ入力・キャッシュ書き込み・キャッシュ読み・出力・うち思考のトークン）
- `stop_reason`、拒否の種類（`stop_details.category`）、実際に応答したモデル
- 本文の JSON がスキーマに合うか

既定の条件は `claude-opus-5-5:low`、`claude-opus-5-5:medium`、`claude-opus-5-5:low:fast`、
`claude-sonnet-5-5:low`、`claude-haiku-5-5:low`。

> **時間だけを測る。発言の質は見ていない。** JSON がスキーマに合うかは数えるが、推理や日本語の
> 良し悪しは判定しない。速い条件が見つかっても、そのモデル・effort でゲームの評価を回し、
> 品質が落ちないことを確かめてから既定を変える。**別のモデルに替えるかどうかはオーナーが決める。**

### 1.2 仕組み

1. **記録（無料）**: `--seed` のオフライン対戦（v3・全17席AI）を1試合、`ScenarioProvider` で
   回し、送られたプロンプトをすべて記録する（`backend/app/eval/prompt_capture.py` の
   `CapturingProvider` と `capture_offline_game`）。推理エンジンの組み立ては
   `app.ai.engine_mode` から取り、フェーズの進め方は `evaluate.py` と同じなので、記録される
   のは本物の v3 のプロンプト（盤面メモ・チャットの発言スキーマ `ChatDiscussionOutput` 込み）
   である。1試合で約160〜190件、15秒ほどかかる。
2. **標本**: そこから `--prompts` 件（既定60）を、スキーマごとの割合で選ぶ
   （議論 約40%・投票 約30%・夜行動 約15%・狼/共有チャット 約15%）。同じシードなら同じ標本に
   なる。足りないスキーマの分は、ほかのスキーマで埋める。
3. **実測（有料）**: 1件のプロンプトを、すべての条件で続けて送る。条件の順はプロンプトごとに
   1つずつずらす（いつも同じ条件が先頭や最後にならないように）。比べる条件はすべて同じ時間帯・
   同じ回の中で測る。プロンプトを送る順は、スキーマと日を混ぜてある。費用の上限で途中で
   止まっても、測れた部分の構成が序盤の短いプロンプトに偏らない。
4. 要求の形はプロバイダ（`anthropic_claude.py`）と同じ: モデル、`max_tokens` の下限
   （`WEREWOLF_ANTHROPIC_MAX_TOKENS`、既定12000）、`output_config` の effort と JSON schema
   （`anthropic.transform_schema`）。違いは次の3点だけで、どれも時間をそのモデルだけのものに
   するため。
   - 拒否時のフォールバック（beta）を送らない。別モデルが答え直すと、時間が混ざる。
   - SDK とスクリプトの再試行をしない。再試行した要求の時間は、1回の要求の時間ではない。
     失敗はそのまま行として記録する。
   - `speed="fast"` は fast の条件にだけ付ける。
   この形は `tests/scripts/test_latency_sweep.py` がプロバイダの組み立てと突き合わせて
   固定している。
5. 同時に送るのは `--concurrency` 件（既定4）まで。キーと接続先は、アプリの設定
   （`WEREWOLF_ANTHROPIC_API_KEY`・`WEREWOLF_ANTHROPIC_BASE_URL`）から明示して SDK に渡す。
   SDK 自身の `ANTHROPIC_*` は読まない（§11.2）。プロンプトキャッシュは使わない（プロバイダも
   使っていない）。

### 1.3 ローカルで回す

```bash
cd backend && source .venv/bin/activate

# 計画と費用の見積もりだけ(通信なし・キー不要・費用ゼロ)
python scripts/latency_sweep.py --dry-run --max-cost 5

# 実測(有料)。--max-cost は必須
WEREWOLF_ANTHROPIC_API_KEY=... python scripts/latency_sweep.py --max-cost 15

# 条件・件数を変える
python scripts/latency_sweep.py --dry-run \
    --configs claude-opus-5-5:low,claude-opus-5-5:low:fast --prompts 30 --seed 2
```

`--configs` は `model:effort` または `model:effort:fast` のカンマ区切り。effort は
`low`・`medium`・`high`・`xhigh`・`max`。fast は単価表に fast の行があるモデル（いまは
`claude-opus-5-5`）だけ。形が違う・同じ条件が2回ある、といった入力は、何も送る前に止める。

出力（`--out`、既定 `eval-out/latency-sweep/`。`eval-out/` は git の対象外）:

| ファイル | 中身 |
|---|---|
| `plan.md` / `plan.json` | 計画: 標本の構成、要求数、条件ごとの最悪・見込みの費用 |
| `prompts.jsonl` | 標本のプロンプト全文（オフライン対戦のもの。シードとコミットから再現できる） |
| `rows.jsonl` | 1要求1行の測定値。終わった要求から追記するので、途中で止めても残る。本文の JSON がスキーマに合わなかった行は、本文の先頭2000字（`invalid_text`）と最初の検証エラー（`validation_error`）も持つ。2026-11-16 の測定では、fast の議論で1件だけ合わなかった答えの中身が残らず、原因を読めなかったため |
| `rows.csv` | 同じ内容の CSV |
| `summary.md` / `summary.json` | 条件 × スキーマごとの集計 |

### 1.4 Actions で回す

ワークフロー「レイテンシ測定」（`.github/workflows/latency-sweep.yml`）を手動で実行する。

| 入力 | 既定 | 中身 |
|---|---|---|
| `configs` | 上の5条件 | 測る条件 |
| `prompts` | `60` | 標本の件数（1〜1000） |
| `seed` | `1` | 記録する対戦と標本のシード |
| `max_cost` | `5` | 推定費用の上限（USD、200まで） |
| `dry_run` | オン | オンなら計画と見積もりだけ。**外すと実測する（有料）** |

- キーは secret の `WEREWOLF_ANTHROPIC_API_KEY`。dry_run のときは、キーをステップに渡しも
  しない。接続先を変えるときは、リポジトリの変数 `WEREWOLF_ANTHROPIC_BASE_URL`（空なら既定）。
- 入力はすべて環境変数でシェルに渡し、形を確かめてから使う（スクリプトの本文に入力を
  埋め込まない）。
- 同時実行のグループ `ai-evaluation` を評価のワークフローと共有する。同じキーとレート上限を
  使うので、同時に走ると互いの時間を乱す。あとから起動したものは待つ（先のものを止めない）。
- 結果（なければ計画）を実行画面のサマリーに出し、出力一式（`backend/latency-out/`）を
  成果物として90日残す。

### 1.5 費用

- 各要求の前に、その要求の**最悪の費用**（`max_tokens` をすべて使った場合）を
  `EvaluationBudget.reserve` で予約し、終わったら実際の費用（usage と
  `app/ai/provider/pricing.py` の単価、fast の条件は fast の行）で `settle` する。
  上限に入りきらない要求は、送っている最中の要求が精算されるのを待ってからもう一度試し、
  それでも入らなければそこで止める。送った分の結果は残り、集計には「費用の上限で止めた」と出る。
- 失敗した要求は、プロバイダと同じ考え方で数える: 4xx は0、それ以外（5xx・タイムアウト・
  切断）は入力分。
- 既定の60件 × 5条件（300要求）の見積もり（シード1、2026-11-16 の単価表）:
  最悪 約$74、見込み 約$13。見込みは effort ごとの出力トークンの仮定（low 800・medium 2000・
  high 4000・xhigh 6000・max 8000）による概算で、実測ではない。
- **既定の上限 $5 では、見込みどおりなら60件のうち約22件まで**測れる（計画にこの数が出る）。
  条件はプロンプトごとに並べて送るので、どこで止まっても各条件の件数はそろう。全件を測るには
  `max_cost` を見込みより少し高く（例: 15）する。最悪の費用まで上げる必要はない（予約は1要求
  ごとで、精算されれば次に回る）。

### 1.6 結果の読み方

`summary.md` の表は条件 × スキーマごとに1行、最後に条件全体の行がある。

- **成功**: ストリームが最後まで届き、本文の JSON がスキーマに合った要求。
- **最初の文字**: 最初の本文の断片が届くまで。思考のあいだは何も届かないので、この値が
  ほぼ「話し始めるまでの待ち」になる。
- **完了**: ストリームの終わりまで。今の画面は発言が完成してから出るので、待ちはこちら。
- **5秒以内**: 完了までが5秒以下だった要求の数。
- p50 / p90 は線形補間。件数が少ないと p90 は粗い（n を横に出している）。
- 主に見るのは議論（`ChatDiscussionOutput`）の行。発言は1件ずつ順に生成するので、1回の
  待ちがそのまま会話の速さになる。投票と夜行動は席どうしで並列に走る。
- 拒否・打ち切り（`max_tokens`）・エラーの数も条件ごとに出る。M1 の「拒否率の上限」
  （§11.5）は、ここの拒否の数を見て置く。

この表で決めてよいのは「速さの候補」までである。候補の条件でゲームの評価を回して品質を
確かめ、モデルの変更はオーナーが決める。

## 2. 人間判定（`human_judgment_quiz.py`）

### 2.1 何を答えるか

§6 の目標「評価者が AI/人間 を当てる正答率が60%以下」を測る。ゲームのログをそのまま見せても
測れない。1人 + AI16人の卓では発言の約94%が AI なので、「全部AI」と答えるだけで94%当たる
（§11.5 Phase 4）。そこで、次の条件をそろえた問題を作る（`backend/app/eval/judgment_quiz.py`）。

- **50/50**: 問題のちょうど半分が AI、半分が人間の発言。片方だけ答えると50%になる。
- **長さをそろえる**: 発言を長さの帯（〜19字・20〜39・40〜59・60〜89・90〜129・130字以上）に
  分け、AI の発言1件ごとに同じ帯の人間の発言1件を組にする。「長いのはAI」では当たらない。
- **言葉以外の手がかりを消す**: 発言者の名前は出さない。発言の中の名前は、AI 側も人間側も
  同じように〈A〉〈B〉…の記号に置き換える（記号は発言ごとに A から振り直すので、同じ記号でも
  別の発言では別の人）。席の ID（`p3`）、発言の ID（`[m12]`）、返信のアンカー（`>>12`）も消す。
  AI の席は決まった名前の一覧から名付けられ、人間のログには別の名前が出るので、名前が残ると
  それだけで答えが分かる。
- **再現できる**: 同じ入力と `--seed` なら同じ問題になる（並びもシードで混ぜる）。

AI の発言は `evaluate.py` の対戦記録（`transcript-seedN.json`）の、公開の議論（`kind` が
`discussion`）だけを使う。コードがモデルの代わりに出した定型の発言（`used_fallback`）は、
既定では除く（モデルの発言を問うため。`--include-fallback` で含められる）。同じ文の重複も除く。

### 2.2 人間の発言は、オーナーが用意する

**リポジトリには人間の発言を一切入れていない。** 人間の参照用の発言は、オーナーが自分で用意
する UTF-8 のファイルで渡す。

- テキスト: 1行に1発言。空行と `#` で始まる行は無視。
- JSONL: 1行に1つのオブジェクトで、`text`（必須）。`speaker`（文字列）と `names`（文字列の
  リスト）があれば、その行でその名前を伏せる。
- `--mask-names 名前.txt`（1行1名）で、全行で伏せる名前を足せる（人間のログの参加者名など）。
  短い名前は別の語の中でも置き換わることがある。伏せすぎる側に倒れるので、目隠しの試験としては
  安全側である。

> **権利の注意**: 人間の発言は、たいてい他人の言葉である。公開や再配布の権利が無いかぎり、
> 人間の発言の原文と、それを含む `quiz-sheet.md`・`answer-key.json` はリポジトリに
> コミットしない。採点結果（`score.md`・`score.json`）は人間の発言を含まないように作って
> あり、コミットしてよい。実ログの扱いの原則は `docs/real_game_log_reasoning_plan.md` に従う。

### 2.3 回し方

```bash
cd backend && source .venv/bin/activate

# 1. 問題を作る(--transcripts にディレクトリを渡すと、中の transcript-seed*.json を全部使う)
python scripts/human_judgment_quiz.py build \
    --transcripts eval-out/ \
    --human ~/private/human-lines.txt \
    --mask-names ~/private/names.txt \
    --items 40 --seed 1

# 2. eval-out/judgment-quiz/quiz-sheet.md を評価者に渡す(answer-key.json は見せない)
#    回答は rater,item,guess の CSV(guess は AI か 人間)。
#    同じ場所の ratings-template.csv に、問題の行だけ入った雛形がある。

# 3. 採点する(評価者ごとのファイルを並べてよい)
python scripts/human_judgment_quiz.py score \
    --key eval-out/judgment-quiz/answer-key.json --ratings ratings-*.csv
```

`build` は、長さの帯ごとの候補数と使った組の数を表示する。人間の発言が足りない帯があると、
問題は `--items` より少なくなる（そのことも表示する）。回答の CSV に、知らない問題番号・
同じ評価者の同じ問題への二重回答・`AI`/`人間` 以外の答えがあれば、行番号つきでまとめて止める
（`ai`・`human` などの綴りは受け付ける。空欄の行は数えずに件数だけ出す）。

### 2.4 統計

- 正答率と、その**片側95%上限（Clopper-Pearson、二項分布の正確な上限）**を出し、上限が60%
  以下なら「示せた」とする。Clopper-Pearson は名目の信頼度を下回らない（やや保守的な）方法で、
  正規近似（Wald）より幅が広い。
- 評価者ごとの正答率、AI の発言を当てた率と人間の発言を当てた率を分けて出す（両者が大きく
  違えば、評価者がどちらかに寄って答えている）。
- 見抜かれやすかった AI の発言を5件まで出す（ドクトリンと口調の例を直す手がかり。§7 Phase D）。
- **必要な判定の数**: 観測された正答率が真の値どおりだったときに、上限がちょうど60%に届く数。

  | 真の正答率 | 正規近似（§11 の数） | Clopper-Pearson（この採点の上限） |
  |---|---:|---:|
  | 50% | 約68 | 約76 |
  | 55% | 約268 | 約289 |

  §11 の「約70・約270」は正規近似 `n = z² p(1−p) / (0.60 − p)²`（z = 1.645）の値。
  この採点は Clopper-Pearson で判定するので、実際に要るのは右の列である。どちらも
  「届く確率がおよそ半分」の数なので、余裕を持って集める。
- 各判定を独立とみなしている。少ない評価者が少ない発言を何度も判定すると、上限は実際より
  楽観的になる。評価者を複数にし、発言の数も十分にとる。

## 3. 記録の扱い（常設のルール）

§11.6 のとおり、残す価値のある結果は `backend/artifacts/` にコミットする。Actions の成果物は
保持期間が切れると消える（レイテンシ測定も評価のワークフローも90日）。run #11 の
対戦記録はこれで失われた。

- ディレクトリを1回の測定ごとに作り（例: `backend/artifacts/latency-sweep-2026-11-20-seed1/`）、
  `README.md` にコミット SHA・条件（モデル・effort・速度）・シード・件数・上限・日付を書く。
- レイテンシ測定: `summary.md`・`summary.json`・`rows.csv`・`plan.json` を入れる。
  `prompts.jsonl` はシードとコミットから再現できるので任意。
- 人間判定: `score.md`・`score.json` と、使った対戦記録のシード・問題の作り方（`--items`・
  `--seed`）を入れる。人間の発言を含むファイル（`quiz-sheet.md`・`answer-key.json`・
  回答の元にした人間のログ）は、§2.2 の権利の注意に従う。
- 測定の結果でモデルや effort の既定を変えるときは、その根拠になった成果物のパスを、変更の
  コミットか `docs/approach-reset-2026-10.md` に書く。
